# Operations

The active production scope consists of two bounded Federal Reserve sources: the reporting-forms overview pilot (two exact URLs) and the selected-detail pilot (five exact form URLs for recently updated forms). The detail pilot additionally admits only links labelled `Current` under `/apps/reportingforms/Download/`; historical downloads and other catalogue pages remain excluded. Current PDF and ZIP attachment content is compared alongside each landing page. ZIP bundles are read in memory only; archive member paths, entry counts, compression ratios, and uncompressed size are checked, and unsupported member types fail extraction rather than silently dropping content. Both sources use exact page allowlists; the detail pilot establishes a quiet baseline on its first successful scan. Newly configured sources may have no discovery metadata until their first scan; the CI validator allows that bootstrap state only when no prior inventory, report, history, checkpoint, or discovery ledger exists. The monitoring workflow runs every six hours and can also be started manually for an active configured source. Historical EBA configuration and discovery data remain in the repository for audit and recovery purposes but are inactive.

## Required secrets

- **OPENROUTER_API_KEY** enables AI analysis. Deterministic comparison and evidence collection can still run if AI is unavailable.
- **NTFY_TOPIC** is the optional destination for ntfy alerts. If it is not configured, notification candidates are retained in the notification outbox and can be delivered after a topic is configured.
- **SLACK_WEBHOOK_URL**, **TEAMS_WEBHOOK_URL**, **ALERT_WEBHOOK_URL** (all optional) add alert channels beside ntfy. Slack takes an incoming-webhook URL; Teams takes the URL of a "Post to a channel when a webhook request is received" workflow (Adaptive Card); the generic webhook receives a `changesentinel.alert.v1` JSON document (for n8n, Zapier or a ticketing bridge), signed with `X-ChangeSentinel-Signature: sha256=<HMAC-SHA256 of the body>` when **ALERT_WEBHOOK_SECRET** is set. URLs must be https without credentials. Delivery is tracked per channel: a notification stays queued until every enabled channel has it, and a retry sends only the channels that are missing. Run the monitor workflow with *test_notification* to send a test to every channel.
- **HEALTHCHECK_PING_URL** (optional) is pinged after every successful scan. Point it at an external dead-man's-switch service (for example a healthchecks.io check with a 14-hour period) so you are alerted even when GitHub Actions cannot start jobs at all.
- **AI smoke test**: `.github/workflows/ai-smoke-test.yml` publishes a status for every pull request, but only calls the model when AI-relevant source/evaluator files change; documentation-only and unrelated PRs retain a successful workflow check without consuming provider calls. Relevant `main` pushes and manual dispatches also run the evaluation. The workflow validates the nine-field output contract and evaluates 15 historical parser-artifact cases plus 12 semantic-AI cases (6 relevant regulatory changes and 6 cosmetic/irrelevant changes). Each semantic-AI case runs twice; end-to-end accuracy, semantic-AI-only accuracy, and repeat verdict agreement must each be at least 80%, with zero decision-source mismatches. The JSON output reports actual provider model IDs per call so free-router selection changes are observable. Every fixture must declare its expected decision source. The free router remains the default; invalid/empty responses count as incorrect and unstable. Fork PRs skip the secret-dependent model job but still run normal CI. The workflow does not change monitoring state or send ntfy notifications.

## Workflow behavior

- **RegMonitor CI** tests code pushes to main and pull requests. Pushes affecting only monitoring data are intentionally excluded from CI.
- **Regulatory Monitor** wakes every six hours or on manual dispatch. A scheduled run scans only the monitors their scan schedule makes due (see *Scan schedules* below); a manual run scans every source it names. Post-run validation considers only active sources selected for that run; inactive historical metadata must not block an active run.
- A paused discovery source must have a valid, non-empty resumable checkpoint. The workflow queues continuation runs for every selected source that is paused.
- Monitoring state, snapshots, history, notification delivery state, and pending notifications are committed under the data directory.
- **Deploy Monitoring Console** publishes index.html, dashboard.js, dashboard-lib.js and the core JSON files (`dashboard-v2.html` now only redirects to the main page). Snapshot and evidence files are read from the repository's raw-content endpoints.
- **Monitor Freshness Check** runs every three hours and alerts (ntfy) when any monitor is overdue: 8 hours past the scan slot its schedule expected it in (14 hours after the last scan for the default six-hourly schedule).
- **Update Monitor Settings** applies owner-submitted `[ChangeSentinel] Update monitors` requests from the dashboard (scan schedules for one monitor or a preset for many) to `config/sources.json`.
- **RegMonitor CI** also runs the golden extraction corpus check and full persisted-state validation.

## Scout

- **Scout** runs every Monday at 04:17 UTC, or on manual dispatch with `regulator` set to `all`, one id or a comma-separated list. It needs no secrets. A sweep that is not `COMPLETE` raises a workflow warning; the dashboard's Coverage panel shows each channel's note.
- **The first sweep is a baseline.** It records what each regulator already publishes and announces nothing; new pages appear from the following week. The *Backlog* filter lists already-published pages that look relevant.
- **Adding a regulator or channel from the dashboard:** Scout → Sources → *Add a source* (or *Add channel* / *Edit details* on a regulator). The prefilled issue is applied by **Scout Source Request** only when the owner opened it; the merged `config/scout.json` must validate, new hosts must resolve to public addresses, and a channel address already used elsewhere is refused. The regulator is then swept once. Removing a channel or changing budgets remains a reviewed edit of `config/scout.json`.
- **Adding a regulator by hand:** add a profile to `config/scout.json` (hosts, channels, optional path hints, keywords, known gaps), run `python -m regmon.scout sweep --regulator <id> --data-dir /tmp/scout` locally or dispatch the workflow for that id, and check the Coverage panel. Paginated listings must declare `newest_first`; a listing whose content selector stops matching fails loudly rather than reading the whole page.
- **Reading the findings:** the list opens grouped by kind of publication (or by regulator, or by the day Scout found them), with a digest line, a three-light evidence meter on each finding and a *Strong only* filter. Long lists show the first few findings of each group until it is opened. A finding's detail explains why Scout surfaced it, then previews the page itself, or the listing page it was found on with the link marked, through the same page reader and sandbox as Add a link (with a phone-width view and a full-screen view).
- **Reviewing:** "Monitor this page" uses the normal owner-only registration flow. Several findings can be selected at once: *Monitor…* opens them, ticked, in the Add a link checklist, and *Not relevant* records up to 30 of them in one request. "Not relevant" and "Restore" open an issue processed by **Scout Review Decision**, which records the decision for that address only, rebuilds `data/scout/review.json`, closes the issue and republishes Pages.
- Sweeps and review decisions share the `scout` concurrency queue; Scout and monitor state commits are scoped to their own paths and never block each other.

## Add a link: explore or follow by level, then confirm

- **Explore the page:** the dialog shows the page through the **page-reader** Edge Function (`supabase/functions/page-reader`). It fetches one public page (public addresses only, re-checked at every redirect; 8 MB, 20 s per request and 34 s per read; Ask Sentinel's origin allowlist; a signed-in or visitor identity; a per-instance request budget) and returns a script-free copy with every link numbered, plus the links with their text and the heading above them.
  - *Getting the page:* it names itself like the monitor (`Mozilla/5.0 (compatible; ChangeSentinel/0.6 page reader; …)`); a 401/403/406/409/429/503, a dropped connection or a bot-check page is retried once with ordinary browser headers. Session cookies set during the read are sent back on its redirects, and `<meta http-equiv="refresh">` or a one-line script redirect on an otherwise empty page is followed. A bot check that survives the retry is reported in words, not shown.
  - *Making the copy readable without script:* loading screens and splash overlays are removed, content waiting for a scroll animation or an anti-flicker snippet is revealed, lazy images get their real address, stylesheets switched on by an `onload` handler (`rel=preload`, `media=print`) apply, `<noscript>` images are shown, and relative `url()` references in inline styles are made absolute. Links that exist only as `onclick="location.href=…"`, `javascript:open('…')` or `data-href` are collected. A page that builds itself with script carries a notice, and the addresses in its embedded data are listed.
  - *Showing it:* the copy is shown in `<iframe sandbox="allow-scripts">` without `allow-same-origin`, so it runs in an opaque origin and cannot reach the dashboard, its storage or its cookies. The reader's own policy is replaced by one that admits a single bridge script by nonce (no network, frames, workers or forms). The bridge reports clicks to the dashboard by `postMessage`, which accepts them only from that frame and with that load's token: a click opens a page in the frame, Shift-click (or *Tap selects* on touch screens) selects a link. Safari never runs listeners that the parent page attaches inside a script-less sandboxed frame, which is why selection lives in the frame. Links in site menus, headers and footers are flagged and left out of the side list, but stay clickable.
- **Follow links by level:** the browser reads the starting page and the pages it links to through the same function, up to 1 / 60 / 150 pages for levels 1 / 2 / 3, only on the starting host and within the chosen folder. Every link found is listed (menus excepted); nothing is ticked for you.
- **Confirm:** one checklist for both methods, grouped by page and heading. Ticked links go out through the existing owner-only bulk request, at most 25 per request. Already monitored or stopped addresses are shown and left out. The work in progress is kept in the browser until *Done* or *Start over*.
- **Weekly check (optional, after following links):** opens an Add-monitor request with `Discovery only: yes`, so **Register Dashboard Monitor** saves a depth-limited Scout channel (`explore_prefixes`, and `document_hosts` for other hosts whose documents were found) and adds **no** monitor. New links then appear in Scout for review. Scout never fetches document hosts.
- **Deploying the reader:** `supabase functions deploy page-reader --project-ref pysoukwmnwwgilkwafdy --no-verify-jwt` (it checks the identity itself, like Ask Sentinel). Without it, *Explore* shows a clear error and the rest of the dashboard is unaffected.

## Alert reliability

Every run queues its notification candidates in the durable outbox and commits the monitoring state **before** anything is sent; delivery happens only after that commit succeeds, and the delivery ledger is committed afterwards. If the state commit cannot be published, nothing has been sent and the next run re-detects the same events. The commit helper (`scripts/commit_state.sh`) rebases the data-only commit when `main` advanced with code-only commits, and refuses when another run committed `data/` in the meantime.

The ledger is saved after each successful delivery, so a cancelled or crashed job can re-send at most one message. Delivery is at-least-once: interruption after ntfy accepts a message but before the ledger commit can still cause a duplicate.

Persistent fetch or extraction errors alert once per episode (URL + error class + onset), not on every run; each observation still writes its own evidence. `defaults.error_alert_after_runs` (1–28, default 1; production uses 2) sets how many consecutive failing scans of a resource are needed before its episode alerts, so a one-off timeout on a regulator site is recorded without paging anyone. The alert then states how many scans have failed and since when.

Every scan also rebuilds `data/health.json` (`python -m regmon.health`): totals, 7- and 30-day check/failure/change/alert volumes, a 14-day daily series, and rosters of failing monitors (with onset and failing-scan count), stale monitors (overdue against their own scan schedule), each monitor's schedule and next due slot, the expected schedule load for the next 7 days, inactive monitors (no content change for 45+ days) and monitors whose address carries a past year (e.g. `circulares-2025`) and has been quiet for 30+ days. It is derived from committed state only and never affects detection; Pages publishes it with the dashboard, where the **Health** view (rail; on phones, from the Overview's *Monitor health* block) lists failing, stale, quiet and year-stamped monitors with 7- and 30-day volumes and a 14-day chart. The **Alerts** view shows which channels recent alerts reached and how to add Slack, Teams or a webhook. A failed workflow run sends a "Regulatory Monitor run failed" ntfy alert, and the **Monitor Freshness Check** workflow alerts when a monitor is overdue for its scheduled scan (for six-hourly monitors, 14 hours: two missed slots, since GitHub routinely delays scheduled runs by an hour or more).

## Per-monitor alert conditions

A single-page monitor can carry a plain-language condition. Set it from a page's header (**Alert me when…** / **Edit alert condition**, also on the monitor's Health page), once for every new monitor in the **Add a link** review step, under **Add a link → Monitor only this exact address**, or as `alert_condition` in `config/sources.json`. Each opens a prefilled GitHub request that the owner-only workflow applies. Detection is unchanged: every technical change is still detected, saved and diffed. The AI additionally returns `condition_met` and `condition_reason`, kept beside (not inside) the nine-key analysis.

- Condition met: the change alerts, even if the AI judged it not relevant in general (the owner asked for it). The alert carries an "Alert condition" line.
- Condition not met, **Alert only when it is met** ticked (`alert_only_on_condition`): no alert; the change is recorded at low priority and shows "Condition not met" in the dashboard. If a generic alert was already delivered, a low-priority follow-up says the condition was not met.
- Condition not met, box unticked: the normal relevance rule applies.
- AI unavailable or invalid: the generic "Technical change detected" alert still goes out, so a monitor never goes silent because the model failed.

Resubmitting the same address with a new condition updates it; an empty **Alert me when** line clears it. Conditions can only be set on monitors that watch one page.

## Legacy canonical URL collisions

Run `python scripts/migrate_legacy_url_collisions.py --source eba-consumer-protection` for a read-only preflight. It groups inventory IDs using the current canonicalization rule and reports the survivor it would choose, whether normalized hashes/snapshots agree, and any reason a group is unsafe. The tool is dry-run by default.

Applying a migration requires an explicit source selection: `python scripts/migrate_legacy_url_collisions.py --source eba-consumer-protection --apply`. The tool only modifies `data/latest.json`, only for inactive sources, and only where every record has the same non-empty normalized hash and a valid text snapshot and there are no conflicting pending AI work items. It prefers a trusted baseline, then the exact configured URL spelling, then the most recently checked record, then a deterministic lexical tie-break. Duplicate change histories are merged into the survivor; immutable evidence, snapshots, historical reports, run history, and the notification ledger are left untouched. Conflicting baselines or missing snapshots are reported and skipped for manual review.

Do not reactivate either EBA source just to test this migration. Review the dry-run plan, apply one selected inactive source in a reviewed change, run state validation and CI, and verify the following scan does not emit a removal for the query-order duplicate.

## Safe monitor registration

The dashboard registration workflow is owner-only. Registration rejects credential-bearing URLs and obvious private/internal addresses, bounds each manually registered source to one exact URL, and validates CSS selectors. A duplicate URL with different CSS selectors is rejected rather than silently reusing the old configuration.

Redirect targets are checked and discovery redirects must stay within the current monitor scope. DNS preflight checks reduce SSRF risk but cannot fully prevent deliberate DNS rebinding; use outbound network egress controls for high-assurance deployments.

## Manual verification checklist

1. Require RegMonitor CI to pass before merging code changes.
2. Run AI Smoke Test after changing AI configuration and confirm it reports `smoke_test: passed`.
3. Verify a genuine changed-content run yields an AI status of `ok`, `invalid`, `error`, or `skipped` in the report counts before concluding the AI path is healthy.
4. Confirm the existing `fed-reporting-forms-pilot` remains complete and `fed-reporting-forms-detail-pilot` completes its landing-page plus current-attachment baseline. Verify historical links and non-allowlisted report pages are absent from the discovered inventory, then confirm the state commit and dashboard refresh. Check that ZIP attachments have `extraction_type=zip` with no extraction errors.
5. Configure NTFY_TOPIC and dispatch test_notification=true to verify delivery.
6. Keep regression coverage for transient delivery failures, confirming queued events persist and are retried.
7. Do not reactivate eba-full-site to clear stale metadata. Select and bound the intended source explicitly.
8. If a REMOVAL_HELD alert arrives, inspect the source first. Only when the pages were really retired, dispatch **Regulatory Monitor** with `source_id` and `allow_mass_removal` both set to that source ID.
9. After any prompt, model, evaluation fixture, or drift-guard change, require AI Smoke Test to pass the 80% end-to-end, 80% semantic-AI-only, and 80% repeated-verdict-agreement gates; confirm zero decision-source mismatches and that all 12 semantic-AI cases ran twice.
10. Dependencies are pinned exactly. To upgrade one, change `requirements.txt` in a PR; if the golden corpus check fails, either pin back or bump `CONTENT_EXTRACTOR_VERSION` deliberately.

## Regulators, Excel templates, documents and document rules

- **`config/regulators.json`** maps hosts to a regulator, jurisdiction and region. The heatmap groups and labels monitors with it ("Group by" → Regulator / Jurisdiction / Region / Kind / Site). Add a regulator by adding an entry with its `hosts`; unknown hosts fall back to the site name. Pages copies the file to `site/config/`.
- **Excel monitoring.** `.xlsx`/`.xlsm` files are extracted by `regmon/workbook.py` (profile `xlsx2`): every sheet (with hidden/very-hidden state), formulas with their saved results, merged ranges, data-validation rules and named ranges. Rows carry their sheet and column letters but not row numbers, so an inserted row is one change. Existing workbook baselines re-baseline quietly once on the new extractor. The dashboard draws a cell-by-cell comparison (row-aligned, renamed/added/removed sheets, formula vs value changes) from the saved originals.
- **Documents in the dashboard.** PDFs, Excel, Word and ZIP files open inside the dashboard (Scout, Explore, snapshots). The page reader returns the file whole when asked with `{"mode": "file"}` — **redeploy the `page-reader` Edge Function** after merging.
- **Smarter Add a link (Explore).** The side panel opens on **Suggested**: forms, templates, instructions and other regulatory documents ranked first, with menus, careers and news pushed down and older years or superseded copies held back. **Shift-drag** draws a box on the page and **Pick a part** (tap-friendly) selects a table, list or section; the selected area can have its links selected, or become **Watch only this part** (the page's include selector) or **Ignore this part** (an ignore selector, e.g. a "last updated" banner). These page rules travel with the link request. After a pick, **Select similar** offers one-click rules ("All PDFs starting “Current”", "All PDFs under “Forms”"). Follow links by level gets the same Suggested filter, **Hide older versions** and **Tick similar**.
- **Make this a monitoring rule.** With documents selected on a page, Explore proposes a rule from them — the folder they sit in and the label they share (for example `^Current`) — shows how many documents on the page match today and outlines them on request, then opens the owner request below. Documents the rule covers are left out of the ordinary link requests so nothing is registered twice.
- **Document rules.** A single add request may carry `Documents under:` (up to 5 folder addresses) and `Document link text matches:` (one regular expression, ≤200 characters) with `Crawl depth: 1`. The monitor then watches that page plus only the documents it links to in those folders whose link text matches — new ones are picked up automatically, nothing else on the site is followed. Discovery binds pages to `allowed_urls` whenever `allowed_resource_prefixes` is set.

## Cadence additions

- **Plan a filing** lays out a periodic return's next due dates: monthly, quarterly (any financial year end) or yearly, a filing lag in days after period end (with a separate lag for the year-end period), weekend due dates moved to the next business day (public holidays are not modelled), and team steps a number of business days before each filing (data cut-off, review, sign-off by default). The preview shows every date; editors add them to the shared calendar in one go (entries already on the calendar are skipped), anyone can download them as one `.ics`.
- **Next 12 weeks** strip above the calendar shows how much is due each week; weeks with three or more deadlines, and days with two or more, are flagged as clashes. It follows the search, type and owner filters.
- **Owner filter** narrows the calendar, agenda and load strip to one owner's entries.
- **Source flags**: an entry whose source link is a monitored page shows whether ChangeSentinel saw it change in the last 45 days (with **View change**), or that it is monitored and quiet; an unmonitored source offers **Monitor this source**.
- **Track this** turns a date ChangeSentinel detected into a team entry (owner, reminder) in one step.
- Every entry can be added to **Google Calendar** or downloaded as a single **.ics** for Outlook or Apple Calendar.

## Scan schedules

Each source may set its own cadence in `config/sources.json`; all fields are optional and the defaults keep the six-hourly scan (`regmon/schedule.py`):

| Field | Values | Meaning |
|---|---|---|
| `check_every_hours` | 6, 12, 24, 48, 72, 168 | Minimum spacing between scans. A run counts as on time if it starts up to 3 hours early relative to the last scan, so GitHub's late starts never push a daily check to the next day. |
| `check_days` | list of `mon` … `sun` | Weekdays a scan may run on. |
| `check_hours` | `[start, end]`, whole hours, at least 6 apart | Local hour window a scan slot must start in. |
| `check_timezone` | IANA name, e.g. `America/Sao_Paulo` | Zone the days and hours are read in (default UTC). |

A scheduled run passes `--due-only`: a source is scanned when it has never been scanned, its discovery is paused mid-crawl, or its cadence makes it due. Sources left for later are listed under `schedule.not_due` in `data/report.json`, with their next due slot. If no source is due, the run writes nothing. Set schedules from the dashboard (**Scan schedule** on a page or in Health); the dashboard opens a prefilled request that the Update Monitor Settings workflow validates and commits.

## Workspaces, labels and presets

`workspace` (one name, e.g. `NAM`, `EMEA`, `LATAM`, `NTS`) and `labels` (up to 12 free tags) are optional per source; names are 1–40 letters, digits, spaces or `& / + . - _`. They group and filter the dashboard (the scope bar above Pages, Changes and Health, and *By workspace* in the scan field) and never affect detection. Without a workspace a monitor is grouped by its regulator's region. In **Pages → Select**, pick monitors and change their scan schedule, workspace and labels, or apply a preset (release pages every 6 h; specs daily on weekdays; regulator business hours; annual documents weekly; or copy another monitor's settings). Each change is an `[ChangeSentinel] Update monitors` request; label edits add or remove labels without touching others. Add a link's review step and bulk imports can set a workspace and labels for the new monitors (`Workspace:`/`Labels:` request lines, or per-row `workspace`, `labels` and `check_every_hours` in a bulk request).

## Moving from Visualping: import and shadow comparison

**Import.** In *Add a link → Upload a spreadsheet or import from Visualping*, choose a CSV/XLSX list or another tool's export. Columns are found by header: URL (also *Page*, *Website*…), name (*Description*, *Job name*…), workspace (*Workspace*, *Folder*…), labels (*Labels*, *Tags*), frequency (*Frequency*, *Interval*…; matched to the nearest scan schedule, fastest every 6 hours) and status (*Paused*/*Inactive* rows are left out). Pages already monitored are left out. Up to 2,500 links are sent as requests of 25; each request carries per-row `workspace`, `labels` and `check_every_hours`. Per-page alert conditions are not imported (the summary says how many the file had).

**Shadow mode.** `shadow: true` on a source means it scans, detects and records as usual but sends no content alerts (changed, new or removed pages) and is left out of digests; operational alerts (fetch/extraction failures, held removals) still go out. Imports can start new monitors in shadow mode; turn it off per monitor or in bulk from **Labels → Alerts → Send alerts**.

**Comparison.** *Alerts → Compare with Visualping* reads Visualping's alert or change history export (a URL column and a date column) in the browser and pairs each Visualping alert with a ChangeSentinel change to the same page within 36 hours. It reports caught by both (with the median lag), only in Visualping (possible misses to open and check), only in ChangeSentinel, and Visualping pages not monitored here (which can be imported in shadow mode). The comparison downloads as CSV; nothing is uploaded or committed.

## Scheduled digests

`config/digests.json` lists daily or weekly digests per workspace (`*` for all): `id`, `workspace`, `frequency` (`daily`/`weekly`), `day` (weekly), `hour` and `timezone`. Each Regulatory Monitor run calls `python -m regmon.digest --due` before alerts are queued. A digest whose latest scheduled time has passed and has not been written is built from the committed run history for its period, saved under `data/digests/<id>/` (the newest in full in `data/digests/index.json`) and queued as a `DIGEST` notification on every alert channel. Each change carries the AI's English summary from the scan and a short verbatim quote of the changed text in the regulator's language; one extra AI call writes a two- or three-sentence overview, falling back to a plain count. A digest added after its time waits for its next one, and only the latest period is sent after missed runs. Set digests up from **Alerts → Digests**; the request is applied by the Update Monitor Settings workflow. `python -m regmon.digest --id <id>` builds one on demand.

## Browser rendering and bot-check pages

`fetch_mode` decides how a source's HTML pages are loaded: `http` (default: a plain request) or `browser` (render every HTML page in headless Chrome, for pages built with JavaScript; validators are not used, since the rendered page can change while the served HTML does not). `browser_wait_seconds` (0–20, default 3) or `browser_wait_selector` decide when a rendered page is read, and `browser_dismiss_cookies` (default on) answers a consent banner with its reject/necessary-only choice. Every request a browser page makes must go to a public http(s) host, and every document load must stay inside the monitor's scope (`regmon/browser_fetch.py`); as with plain fetching, DNS checks reduce but do not remove rebinding risk.

**Bot checks are handled automatically, for every monitor.** When a plain request gets a recognised challenge page (Cloudflare, Akamai, Imperva, PerimeterX, DataDome, AWS WAF, captcha walls; `regmon/botcheck.py`), the URL is opened in headless Chrome straight away. The vendor's check runs there, and once it lets the browser through, the server's own response is kept: a PDF as the PDF, a page as the same HTML a plain request would have got, so the baseline does not depend on how the copy was obtained. To make that work the browser:

- presents itself as ordinary Chrome (no `HeadlessChrome` user agent, no automation flag);
- lets the check's widget frame load from the vendor's host (`CHALLENGE_FRAME_HOSTS`, frames only);
- waits up to 35 s for the check to clear;
- keeps one profile for the run, so after one check the other URLs on that site load at once;
- reads large files in chunks.

It never solves an interactive puzzle. The old `auto` setting is accepted and now means the same as `http`.

When a site keeps showing its check:

- The URL records a `BotCheckError`, and the challenge HTML is saved under `data/snapshots/botcheck/` (named in the record's `bot_check`).
- The last good copy stays the baseline, and every scan tries again.
- After two refusals in a scan, the other URLs on that host wait for the next scan instead of each spending the full wait.
- For `GRACE_HOURS` (24 h) the monitor is *protected, retrying* rather than failing: Health lists it under *Retrying automatically* (`protected` in `data/health.json`), its page shows *Protected site · retrying*, the retries stay out of Changes, and no alert is sent.
- After that it is a failure, alerted **once per site** ("www.ffiec.gov is blocking automatic checks … 43 monitored pages wait"), not once per page.

The scan's URL preflight counts a challenge as reachable. Scout does the same for its channels (`regmon/scout/net.py`): a 403/429/503 that is a bot check is read once through the browser, and a host whose check the browser cannot pass is not retried in that sweep.

`CHANGESENTINEL_CHROME` points at a Chrome or Chromium binary when it is not on PATH. `scripts/browser_challenge_check.py` runs the bot-check path in Playwright's Chromium against a simulated Cloudflare site (`tests/challenge_site.py`): a managed challenge with a widget frame on another host, a clearance cookie only for a non-headless, non-automated browser, and a PDF larger than one DevTools message. CI runs the pydoll path against the same site (`CHANGESENTINEL_BROWSER_TEST=1`).

## Find similar

**Find similar** on a page (Pages → page header) looks for pages like it on demand, in the browser. It starts from where the page is listed: Scout's record of the page that linked it, the monitor's own start page, or the nearest section page (file-store folders are skipped). It follows links two levels within that section and opens the usual Add a link review with the closest matches first. Matches are ranked by another year's edition of the same address, the same report code (FR Y-9C, BCAR, …), the same folder and file type, and shared title words. Nothing is ticked; ticked links become requests as usual, and "Also check weekly for new links" sets up a Scout channel for the section.

## Alert-condition suggestions

The *Alert me when* fields (a monitor's condition dialog, and Add a link's review step) offer starting points drawn from the page itself: report codes found in it (FR Y-9C, BCAR, …), the kind of document it mostly links, and wording about deadlines and effective dates, versions and errata, validation rules, layouts and schemas, consultations and instructions, in English, Portuguese, Spanish, French and German. A monitor's suggestions use its saved text; the review step uses the ticked links (or every link found) and the starting page. They only fill the text box; nothing is saved until the request is submitted.

## Structured spec diffs and the offline compare

When a monitored edit-check workbook, data dictionary, PDF field-spec table, XSD or XBRL linkbase changes, `regmon/spec_diff.py` compares it row by row and the change shows a **Specification changes** sheet (Changes → a change). Tables are recognised by their headers, not positions: a rule table has a rule identifier (Edit No, Rule ID, Check ID, …) and logic, a message or a description; a field table has a field code (Technical Field Name / MDRM, Item code, Data element, Measure name, DPM, formato, campo, …). Rows are aligned by the smallest key that is unique in both versions (rule ID; ID + version; table + ID + version; series + table + ID + version), so an inserted rule is one new rule. XSD elements are keyed by path, code lists by list and value, XBRL assertions by ID (with test, messages, severity and the FFIEC ruleType).

Each changed row gets one category, most important first: new / new version, severity changed (escalated or relaxed, from a Severity column or an edit-type change such as Quality → Validity), logic changed, retired (end date set from 99991231, or Archived / Deprecated / Deleted status), reinstated, effective dates changed, message changed, definition changed, description changed, removed, metadata only, cosmetic only. Retired rules are checked for a live replacement version; added and removed rows that agree on everything but their key are shown as likely re-keyed. The same token swap in a commentary column across many rows (every comment going from "Q1 2026" to "Q1 2027") is shown once as a pattern.

**Declared vs detected.** Regulators annotate rows ("New Rule - Effective Q1 2027", "Updated", "Deprecated", Status "Archived"). Each row's newly declared action is reconciled with what changed, and two kinds of mismatch are listed: a row that changed while still marked as unchanged ("Existing Rule - Remains Effective"), and a row newly marked new or updated with nothing else different. A file seen for the first time shows what it declares about itself instead (**Declared in this file**).

Columns are paired by header, then by role, then by position with a similar header, so a renamed column ("Edit Logic" → "Edit Logic (Excel format)") is still compared and listed as renamed instead of dropped. Punctuation counts in logic, data types, dates, IDs and severities (`X > 0` → `X >= 0` is a logic change, not cosmetic); in messages and descriptions only words count. A version bumped in place with nothing else changed is shown as a new version. In data dictionaries a "Level" or "Severity" column is part of the item's definition, not an edit severity. Metadata and cosmetic rows are capped at 50 listed per table (counts stay exact), so a re-save that touches every row cannot crowd out a logic change.

**Release-notes audit.** When the current file carries its own change log (OSFI's "Version" sheet, a "Revision history" table: version, date, details of change, worksheet), the entries new since the previous copy are checked against what actually changed: counted claims ("Added: 58 rules Deprecated: 8 rules Updated: 33 rules", "-Schedule 10.020 : 16 DPA's …" summed) against the detected counts for the worksheet named, rule or item IDs listed under an action ("Updated rules: IR-1564-20.01-001 …") against how each actually changed, and — when an action lists its IDs — changes of that kind the list leaves out. Differences show at the top of the Specification changes sheet, in the headline and in the workbook's **Release Notes Audit** sheet. On OSFI's BCAR v4 file the notes say 33 conventional rules were updated while 34 rows are marked "Updated Rule".

**Dates in the calendar.** Changed rows that carry dates (Effective Start, End, "Effective Q1 2027") become calendar entries, one per table, date and kind ("Edits: 12 changed rows apply from 2027-03-31 — 10 new, 2 logic changed (0101 v2, …)"), in the dashboard and the .ics feed, marked as read from the specification file.

The result is deterministic, stored in the change's evidence (`spec_diff`, or `spec_inventory` for a new file), summarised on the change (`spec`) and in alerts ("Spec changes: 2 new, 3 retired (1 escalated) — 531 v1, …"), and never stops a scan if it fails. Structure depends on extraction: a PDF whose table comes out as plain prose has no table to compare, and the ordinary redline still applies.

**Offline compare.** The same comparison runs on any two local files, for the quarterly cycle the Excel Compare and Taxonomy Compare tools cover today:

```bash
python -m regmon.spec_diff FRY14Q_2026Q2_CIL_Edits_V1.xlsx FRY14Q_2026Q3_CIL_Edits_V2.xlsx -o Spec_Compare.xlsx --json out.json
```

It reads .xlsx/.xlsm, .csv, .pdf, .docx, .xsd/.xml and .zip packages the way the monitor does, prints the headline, and writes an analyst workbook: **Summary** (both files with SHA-256, counts per table and category), **Spec Changes** (one row per changed item with effective date, severity, before/after, note, the regulator's own annotation, a mismatch flag, an Impact drop-down and Analyst comment), **Cell Changes**, **Patterns**, **Columns** (added, removed, renamed) and **Release Notes Audit**. `--exit-code` exits 2 when substantive changes are found.

**Conformance: our implementation against the spec.** `regmon/spec_conformance.py` compares two *different* files that describe the same rules or items — the regulator's edit checks or data dictionary, and our own rule library, data dictionary or mapping sheet — paired by rule ID or item code whatever their columns and sheet names:

```bash
python -m regmon.spec_conformance FR_Y-9C_edits_2027Q1.xlsx our_edit_library.xlsx -o Gaps.xlsx
```

Findings, most urgent first: **retired in spec, still implemented**; **in spec, not implemented** (live rows only); **implemented differently** (logic, severity, data type, dates or line item disagree — severity compared by rank, so the spec's "Validity" matches our "Error"; for rules with several versions the live one is compared); **implemented, not in spec**. The **Gaps** sheet has Owner, Status (Open / In progress / Fixed / Accepted difference / Not applicable) and Comment columns. `--exit-code` exits 2 when any gap is found, for use in a release pipeline.

## Item registry and downstream impact

`config/registry.json` lists the regulatory data points you report, in any scheme (Federal Reserve MDRM, FR Y-14 data-dictionary fields, FFIEC items, EBA DPM data points and BIRD variables, OSFI DPAs and measures, SBS SUCAVE codes, BCB 5050 accounts, or a scheme you declare under `schemes`), and links each to the **consumers** that read it: tables, views, models, pipelines, reports, checks, dashboards and code paths (`repo` + `path` link straight to the file). `rules` map a pattern such as `BHCK*` to consumers, and `equivalents` link the same data point across jurisdictions. Mappings in `config/lineage.json` are still read, as rules.

When a change touches a registered item (a reporting-item code it added, removed or amended, a rule or field from the structured spec diff, or a registered code named on a changed line, matched exactly as written), the change records a **Downstream impact** (`impact` on the event and timeline, the full list in evidence), the alert carries a *Downstream* line, and the change shows the sentence, e.g. *"These 3 fields in FR Y-9C HC-R change from Q1 2027: BHCK2170, BHCK3210, BHCKC447. They are read by 1 pipeline (FR Y-9C HC load), 1 table (warehouse.fr_y9c.hcr) and 1 model (Capital ratio model)."* The sentence uses the registry as it was when the change was recorded; an older change is read against today's registry and says so.

The **Registry** view lists consumers and items (search, scheme filter), what each consumer reads, the changes that touched an item or anything a consumer reads, and the codes recorded changes touched that are not registered yet. Build the file directly or merge a mapping spreadsheet (one row per item and consumer, columns found by header): `python -m regmon.registry import mapping.csv --write`. `python -m regmon.registry check` validates it (CI runs it) and `python -m regmon.registry lookup BHCK2170` shows what reads a code. A broken registry is reported in the scan log and never stops a scan.

## Measured precision and condition tuning

Each monitor's alerts are scored against reviewers' decisions (Health → a monitor → **Alert precision**; the fleet total and a table per monitor sit on Health → All monitors). A change that alerted and was reviewed Material or Action required is a true positive, Not material a false positive; a change that stayed quiet (AI not relevant, condition not met, markup-only) but was reviewed material is a false negative, and **Report a missed change** records a change the monitor never caught (an owner-only request processed by the Change Review Decision workflow into `data/reviews/ledger.json` → `misses`). Precision = TP / (TP + FP) and recall = TP / (TP + FN + missed), each with a 95% Wilson range, since a monitor gets few reviews. Acknowledged decisions are not counted; shadow monitors are scored on whether the change would have alerted.

From the same records come tuning suggestions: wording that recurs in false alarms and never in material changes becomes an exclusion, wording that material changes share becomes the condition, an "alerts only when met" condition that hid material changes is flagged for broadening, false alarms that were technical-change alerts (AI unavailable) are called out, reported misses point at scope and cadence, and a monitor with five or more false alarms and no true positive is pointed at shadow mode. **Use this condition** opens the usual alert-condition request prefilled; nothing changes until the owner submits it. The arithmetic runs in the browser from the inventory, delivery and review ledgers (so a new decision counts at once) and identically in `python -m regmon.precision`, which prints the same table.

## Recorded browser steps and visual diffs

For the few portals that show their content only after a choice or a click, a monitor loaded with a browser on every scan (`fetch_mode: "browser"`) can carry `browser_actions`: up to 20 steps (`click`, `type`, `select`, `check`, `uncheck`, `press`, `scroll`, `wait`, `wait_for`) replayed after the page loads and before it is read (`regmon/browser_actions.py`). Record them on the portal with the **ChangeSentinel recorder** (Scan schedule → How pages are loaded → drag the link to the bookmarks bar, open the portal, click it, use the page as usual, *Copy steps*, paste): it runs only in your browser, keeps steps across page loads in that tab and never records password fields. Typing into a password field is also refused when steps run, every document load must stay in the monitor's scope, and waits are capped (30 s a step, 90 s in total). A step that fails names itself in the scan's fetch error ("Step 2 (Click #search): nothing matches #search"); the last good copy stays the baseline. `scripts/browser_steps_check.mjs` (CI) records steps on a test portal with the real recorder and replays them with the engine's own in-page script.

`visual_compare: true` keeps a screenshot of each render (`data/snapshots/visual/`, content-addressed; a render that looks the same as the last one reuses its file) and compares it with the previous one (`regmon/visual.py`, Pillow): the share of the page that looks different, the changed regions, and an overlay marking them. Any change on such a monitor carries the comparison, shown under **Visual** in the change's What changed (a divider between the previous and new screenshot, with Marked regions). The text comparison stays the source of truth; with `visual_alert_threshold` (a share of the page, 0.001–1) a page that looks different by at least that much while its text and markup are unchanged raises **VISUAL_CHANGED** ("Looks different"), with its own alert, review and precision like any change.
