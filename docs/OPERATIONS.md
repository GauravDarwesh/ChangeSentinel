# Operations

The active production scope consists of two bounded Federal Reserve sources: the reporting-forms overview pilot (two exact URLs) and the selected-detail pilot (five exact form URLs for recently updated forms). The detail pilot additionally admits only links labelled `Current` under `/apps/reportingforms/Download/`; historical downloads and other catalogue pages remain excluded. Current PDF and ZIP attachment content is compared alongside each landing page. ZIP bundles are read in memory only; archive member paths, entry counts, compression ratios, and uncompressed size are checked, and unsupported member types fail extraction rather than silently dropping content. Both sources use exact page allowlists; the detail pilot establishes a quiet baseline on its first successful scan. Newly configured sources may have no discovery metadata until their first scan; the CI validator allows that bootstrap state only when no prior inventory, report, history, checkpoint, or discovery ledger exists. The monitoring workflow runs every six hours and can also be started manually for an active configured source. Historical EBA configuration and discovery data remain in the repository for audit and recovery purposes but are inactive.

## Required secrets

- **OPENROUTER_API_KEY** enables AI analysis. Deterministic comparison and evidence collection can still run if AI is unavailable.
- **NTFY_TOPIC** is the optional destination for ntfy alerts. If it is not configured, notification candidates are retained in the notification outbox and can be delivered after a topic is configured.
- **SLACK_WEBHOOK_URL**, **TEAMS_WEBHOOK_URL**, **ALERT_WEBHOOK_URL** (all optional) add alert channels beside ntfy. Slack takes an incoming-webhook URL; Teams takes the URL of a "Post to a channel when a webhook request is received" workflow (Adaptive Card); the generic webhook receives a `changesentinel.alert.v1` JSON document (for n8n, Zapier or a ticketing bridge), signed with `X-ChangeSentinel-Signature: sha256=<HMAC-SHA256 of the body>` when **ALERT_WEBHOOK_SECRET** is set. URLs must be https without credentials. Delivery is tracked per channel: a notification stays queued until every enabled channel has it, and a retry sends only the channels that are missing. Run the monitor workflow with *test_notification* to send a test to every channel.
- **HEALTHCHECK_PING_URL** (optional) is pinged after every successful scan. Point it at an external dead-man's-switch service (for example a healthchecks.io check with a 14-hour period) so you are alerted even when GitHub Actions cannot start jobs at all.
- **AI smoke test**: `.github/workflows/ai-smoke-test.yml` publishes a status for every pull request, but only calls the model when AI-relevant source/evaluator files change; documentation-only and unrelated PRs retain a successful workflow check without consuming provider calls. Relevant `main` pushes and manual dispatches also run the evaluation. The workflow validates the nine-field output contract and evaluates 15 historical parser-artifact cases plus 12 semantic-AI cases (6 relevant regulatory changes and 6 cosmetic/irrelevant changes). Each semantic-AI case runs twice; end-to-end accuracy, semantic-AI-only accuracy, and repeat verdict agreement must each be at least 80%, with zero decision-source mismatches. The JSON output reports actual provider model IDs per call so free-router selection changes are observable. Every fixture must declare its expected decision source. The free router remains the default; invalid/empty responses count as incorrect and unstable. Fork PRs skip the secret-dependent model job but still run normal CI. The workflow does not change monitoring state or send ntfy notifications.

## Workflow behavior

- **RegMonitor CI** tests code pushes to main and pull requests. Pushes affecting only monitoring data are intentionally excluded from CI.
- **Regulatory Monitor** runs every six hours or on manual dispatch. Post-run validation considers only active sources selected for that run; inactive historical metadata must not block an active run.
- A paused discovery source must have a valid, non-empty resumable checkpoint. The workflow queues continuation runs for every selected source that is paused.
- Monitoring state, snapshots, history, notification delivery state, and pending notifications are committed under the data directory.
- **Deploy Monitoring Console** publishes index.html, dashboard.js, dashboard-lib.js and the core JSON files (`dashboard-v2.html` now only redirects to the main page). Snapshot and evidence files are read from the repository's raw-content endpoints.
- **Monitor Freshness Check** runs every three hours and alerts (ntfy) when no scan has been saved for 14 hours.
- **RegMonitor CI** also runs the golden extraction corpus check and full persisted-state validation.

## Scout

- **Scout** runs every Monday at 04:17 UTC, or on manual dispatch with `regulator` set to `all`, one id or a comma-separated list. It needs no secrets. A sweep that is not `COMPLETE` raises a workflow warning; the dashboard's Coverage panel shows each channel's note.
- **The first sweep is a baseline.** It records what each regulator already publishes and announces nothing; new pages appear from the following week. The *Backlog* filter lists already-published pages that look relevant.
- **Adding a regulator or channel from the dashboard:** Scout → Sources → *Add a source* (or *Add channel* / *Edit details* on a regulator). The prefilled issue is applied by **Scout Source Request** only when the owner opened it; the merged `config/scout.json` must validate, new hosts must resolve to public addresses, and a channel address already used elsewhere is refused. The regulator is then swept once. Removing a channel or changing budgets remains a reviewed edit of `config/scout.json`.
- **Adding a regulator by hand:** add a profile to `config/scout.json` (hosts, channels, optional path hints, keywords, known gaps), run `python -m regmon.scout sweep --regulator <id> --data-dir /tmp/scout` locally or dispatch the workflow for that id, and check the Coverage panel. Paginated listings must declare `newest_first`; a listing whose content selector stops matching fails loudly rather than reading the whole page.
- **Reading the findings:** the list opens grouped by kind of publication (or by regulator, or by the day Scout found them), with a digest line, a three-light evidence meter on each finding and a *Strong only* filter. Long lists show the first few findings of each group until it is opened. A finding's detail explains why Scout surfaced it, then previews the page itself, or the listing page it was found on with the link marked, through the same page reader and sandbox as Add a link (with a phone-width view and a full-screen view).
- **Reviewing:** "Monitor this page" uses the normal owner-only registration flow. Several findings can be selected at once: *Monitor…* opens them, ticked, in the Add a link checklist, and *Not relevant* records up to 30 of them in one request. "Not relevant" and "Restore" open an issue processed by **Scout Review Decision**, which records the decision for that address only, rebuilds `data/scout/review.json`, closes the issue and republishes Pages.
- Sweeps and review decisions share the `scout` concurrency queue; Scout and monitor state commits are scoped to their own paths and never block each other.

## Add a link: explore or follow by level, then confirm

- **Explore the page:** the dialog shows the page through the **page-reader** Edge Function (`supabase/functions/page-reader`). It fetches one public page (public addresses only, re-checked at every redirect; 8 MB, 20 s per request and 34 s per read; Ask Sentinel's origin allowlist; a signed-in or visitor identity; a per-instance request budget) and returns a script-free copy with every link numbered, plus the links with their text and the heading above them.
  - *Getting the page:* it names itself like the monitor (`Mozilla/5.0 (compatible; ChangeSentinel/0.6 page reader; …)`); a 401/403/406/409/429/503, a dropped connection or a bot-check page is retried once with ordinary browser headers. Session cookies set during the read are sent back on its redirects, and `<meta http-equiv="refresh">` or a one-line script redirect on an otherwise empty page is followed. A bot check that survives the retry is reported in words, not shown.
  - *Making the copy readable without script:* loading screens and splash overlays are removed, content waiting for a scroll animation or an anti-flicker snippet is revealed, lazy images get their real address, stylesheets switched on by an `onload` handler (`rel=preload`, `media=print`) apply, `<noscript>` images are shown, and relative `url()` references in inline styles are made absolute. Links that exist only as `onclick="location.href=…"`, `javascript:open('…')` or `data-href` are collected. A page that builds itself with script carries a notice, and the addresses in its embedded data are listed.
  - *Showing it:* the copy is shown in `<iframe sandbox="allow-scripts">` without `allow-same-origin`, so it runs in an opaque origin and cannot reach the dashboard, its storage or its cookies. The reader's own policy is replaced by one that admits a single bridge script by nonce (no network, frames, workers or forms). The bridge reports clicks to the dashboard by `postMessage`, which accepts them only from that frame and with that load's token: a click opens a page in the frame, Shift-click (or *Tap selects* on touch screens) selects a link. Safari never runs listeners that the parent page attaches inside a script-less sandboxed frame, which is why selection lives in the frame. Links in site menus, headers and footers are flagged and left out of the side list, but stay clickable.
- **Follow links by level:** the browser reads the starting page and the pages it links to through the same function, up to 1 / 60 / 150 pages for levels 1 / 2 / 3, only on the starting host and within the chosen folder. Every link found is listed (menus excepted); nothing is ticked for you.
- **Confirm:** one checklist for both methods, grouped by page and heading. Ticked links go out through the existing owner-only bulk request, at most 25 per request. Already monitored or stopped addresses are shown and left out. The work in progress is kept in the browser until *Done* or *Start over*.
- **Weekly check (optional, after following links):** opens an Add-monitor request with `Discovery only: yes`, so **Register Dashboard Monitor** saves a depth-limited Scout channel (`explore_prefixes`, and `document_hosts` for other hosts whose documents were found) and adds **no** monitor. New links then appear in Scout for review. Scout never fetches document hosts.
- **Deploying the reader:** `supabase functions deploy page-reader --project-ref pysoukwmnwwgilkwafdy --no-verify-jwt` (it checks the identity itself, like Ask Sentinel). Without it, *Explore* shows a clear error and the rest of the dashboard is unaffected.

## Alert reliability

Every run queues its notification candidates in the durable outbox and commits the monitoring state **before** anything is sent; delivery happens only after that commit succeeds, and the delivery ledger is committed afterwards. If the state commit cannot be published, nothing has been sent and the next run re-detects the same events. The commit helper (`scripts/commit_state.sh`) rebases the data-only commit when `main` advanced with code-only commits, and refuses when another run committed `data/` in the meantime.

The ledger is saved after each successful delivery, so a cancelled or crashed job can re-send at most one message. Delivery is at-least-once: interruption after ntfy accepts a message but before the ledger commit can still cause a duplicate.

Persistent fetch or extraction errors alert once per episode (URL + error class + onset), not on every run; each observation still writes its own evidence. `defaults.error_alert_after_runs` (1–28, default 1; production uses 2) sets how many consecutive failing scans of a resource are needed before its episode alerts, so a one-off timeout on a regulator site is recorded without paging anyone. The alert then states how many scans have failed and since when.

Every scan also rebuilds `data/health.json` (`python -m regmon.health`): totals, 7- and 30-day check/failure/change/alert volumes, a 14-day daily series, and rosters of failing monitors (with onset and failing-scan count), stale monitors (no saved scan for 14 hours), inactive monitors (no content change for 45+ days) and monitors whose address carries a past year (e.g. `circulares-2025`) and has been quiet for 30+ days. It is derived from committed state only and never affects detection; Pages publishes it with the dashboard. A failed workflow run sends a "Regulatory Monitor run failed" ntfy alert, and the **Monitor Freshness Check** workflow alerts when no scan has been saved for 14 hours (two missed six-hourly slots; GitHub routinely delays scheduled runs by an hour or more).

## Per-monitor alert conditions

A single-page monitor can carry a plain-language condition, set in **Add a link → Monitor only this exact address → Alert me when** (or `alert_condition` in `config/sources.json`). Detection is unchanged: every technical change is still detected, saved and diffed. The AI additionally returns `condition_met` and `condition_reason`, kept beside (not inside) the nine-key analysis.

- Condition met: the change alerts, even if the AI judged it not relevant in general (the owner asked for it). The alert carries an "Alert condition" line.
- Condition not met, **Alert only when it is met** ticked (`alert_only_on_condition`): no alert; the change is recorded at low priority and shows "Condition not met" in the dashboard. If a generic alert was already delivered, a low-priority follow-up says the condition was not met.
- Condition not met, box unticked: the normal relevance rule applies.
- AI unavailable or invalid: the generic "Technical change detected" alert still goes out, so a monitor never goes silent because the model failed.

Resubmitting the same address with a new condition updates it; an empty **Alert me when** line clears it. Conditions can only be set on monitors that watch one page.

## Legacy canonical URL collisions

Run `python scripts/migrate_legacy_url_collisions.py --source eba-consumer-protection` for a read-only preflight. It groups inventory IDs using the current canonicalization rule and reports the survivor it would choose, whether normalized hashes/snapshots agree, and any reason a group is unsafe. The tool is dry-run by default.

Applying a migration requires an explicit source selection: `python scripts/migrate_legacy_url_collisions.py --source eba-consumer-protection --apply`. The tool only modifies `data/latest.json`, only for inactive sources, and only where every record has the same non-empty normalized hash and a valid text snapshot and there are no conflicting pending AI work items. It prefers a trusted baseline, then the exact configured URL spelling, then the most recently checked record, then a deterministic lexical tie-break. Duplicate change histories are merged into the survivor; immutable evidence, snapshots, historical reports, run history, and the notification ledger are left untouched. Conflicting baselines or missing snapshots are reported and skipped for manual review.

Do not reactivate either EBA source just to test this migration. Review the dry-run plan, apply one selected inactive source in a reviewed change, run state validation and CI, and verify the following scan does not emit a removal for the query-order duplicate.

## Safe monitor registration

The dashboard registration workflow is owner-only. Registration rejects credential-bearing URLs and obvious private/internal addresses, bounds each manually registered source to one exact URL, and validates CSS selectors. A duplicate URL with different CSS selectors is rejected rather than silently reusing the old configuration.

Redirect targets are checked and discovery redirects must stay within the current monitor scope. DNS preflight checks reduce SSRF risk but cannot fully prevent deliberate DNS rebinding; use outbound network egress controls for high-assurance deployments.

## Manual verification checklist

1. Require RegMonitor CI to pass before merging code changes.
2. Run AI Smoke Test after changing AI configuration and confirm it reports `smoke_test: passed`.
3. Verify a genuine changed-content run yields an AI status of `ok`, `invalid`, `error`, or `skipped` in the report counts before concluding the AI path is healthy.
4. Confirm the existing `fed-reporting-forms-pilot` remains complete and `fed-reporting-forms-detail-pilot` completes its landing-page plus current-attachment baseline. Verify historical links and non-allowlisted report pages are absent from the discovered inventory, then confirm the state commit and dashboard refresh. Check that ZIP attachments have `extraction_type=zip` with no extraction errors.
5. Configure NTFY_TOPIC and dispatch test_notification=true to verify delivery.
6. Keep regression coverage for transient delivery failures, confirming queued events persist and are retried.
7. Do not reactivate eba-full-site to clear stale metadata. Select and bound the intended source explicitly.
8. If a REMOVAL_HELD alert arrives, inspect the source first. Only when the pages were really retired, dispatch **Regulatory Monitor** with `source_id` and `allow_mass_removal` both set to that source ID.
9. After any prompt, model, evaluation fixture, or drift-guard change, require AI Smoke Test to pass the 80% end-to-end, 80% semantic-AI-only, and 80% repeated-verdict-agreement gates; confirm zero decision-source mismatches and that all 12 semantic-AI cases ran twice.
10. Dependencies are pinned exactly. To upgrade one, change `requirements.txt` in a PR; if the golden corpus check fails, either pin back or bump `CONTENT_EXTRACTOR_VERSION` deliberately.

## Regulators, Excel templates, documents and document rules

- **`config/regulators.json`** maps hosts to a regulator, jurisdiction and region. The heatmap groups and labels monitors with it ("Group by" → Regulator / Jurisdiction / Region / Kind / Site). Add a regulator by adding an entry with its `hosts`; unknown hosts fall back to the site name. Pages copies the file to `site/config/`.
- **Excel monitoring.** `.xlsx`/`.xlsm` files are extracted by `regmon/workbook.py` (profile `xlsx2`): every sheet (with hidden/very-hidden state), formulas with their saved results, merged ranges, data-validation rules and named ranges. Rows carry their sheet and column letters but not row numbers, so an inserted row is one change. Existing workbook baselines re-baseline quietly once on the new extractor. The dashboard draws a cell-by-cell comparison (row-aligned, renamed/added/removed sheets, formula vs value changes) from the saved originals.
- **Documents in the dashboard.** PDFs, Excel, Word and ZIP files open inside the dashboard (Scout, Explore, snapshots). The page reader returns the file whole when asked with `{"mode": "file"}` — **redeploy the `page-reader` Edge Function** after merging.
- **Smarter Add a link (Explore).** The side panel opens on **Suggested**: forms, templates, instructions and other regulatory documents ranked first, with menus, careers and news pushed down and older years or superseded copies held back. **Shift-drag** draws a box on the page and **Pick a part** (tap-friendly) selects a table, list or section; the selected area can have its links selected, or become **Watch only this part** (the page's include selector) or **Ignore this part** (an ignore selector, e.g. a "last updated" banner). These page rules travel with the link request. After a pick, **Select similar** offers one-click rules ("All PDFs starting “Current”", "All PDFs under “Forms”"). Follow links by level gets the same Suggested filter, **Hide older versions** and **Tick similar**.
- **Make this a monitoring rule.** With documents selected on a page, Explore proposes a rule from them — the folder they sit in and the label they share (for example `^Current`) — shows how many documents on the page match today and outlines them on request, then opens the owner request below. Documents the rule covers are left out of the ordinary link requests so nothing is registered twice.
- **Document rules.** A single add request may carry `Documents under:` (up to 5 folder addresses) and `Document link text matches:` (one regular expression, ≤200 characters) with `Crawl depth: 1`. The monitor then watches that page plus only the documents it links to in those folders whose link text matches — new ones are picked up automatically, nothing else on the site is followed. Discovery binds pages to `allowed_urls` whenever `allowed_resource_prefixes` is set.

## Cadence additions

- **Plan a filing** lays out a periodic return's next due dates: monthly, quarterly (any financial year end) or yearly, a filing lag in days after period end (with a separate lag for the year-end period), weekend due dates moved to the next business day (public holidays are not modelled), and team steps a number of business days before each filing (data cut-off, review, sign-off by default). The preview shows every date; editors add them to the shared calendar in one go (entries already on the calendar are skipped), anyone can download them as one `.ics`.
- **Next 12 weeks** strip above the calendar shows how much is due each week; weeks with three or more deadlines, and days with two or more, are flagged as clashes. It follows the search, type and owner filters.
- **Owner filter** narrows the calendar, agenda and load strip to one owner's entries.
- **Source flags**: an entry whose source link is a monitored page shows whether ChangeSentinel saw it change in the last 45 days (with **View change**), or that it is monitored and quiet; an unmonitored source offers **Monitor this source**.
- **Track this** turns a date ChangeSentinel detected into a team entry (owner, reminder) in one step.
- Every entry can be added to **Google Calendar** or downloaded as a single **.ics** for Outlook or Apple Calendar.
